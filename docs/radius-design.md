# Built-in RADIUS: design

Status: proposal for review (plan.md Section 7, first checkbox). Nothing here is implemented yet.

## Goal

Let a phone or laptop join a WPA-Enterprise SSID on a managed OpenWrt AP with its own username and password, verified by OpenManage itself, without running FreeRADIUS or any other extra service. Failures are audited without logging secrets, and the listener is off unless an administrator turns it on.

## Scope

In scope for the first release:

- One RADIUS authentication listener (UDP 1812) inside the Go process, off by default.
- APs as RADIUS clients, each with its own shared secret, generated by OpenManage and stored encrypted.
- Wi-Fi users ("network users"), separate from OpenManage's own login users (see "Identities").
- One tunnelled EAP method (see "EAP method") with a server certificate OpenManage generates.
- Pushing the AP side (`wpad` with `wpa2`/`wpa3` enterprise, server address, port, secret) through the Section 3 change workflow.

Out of scope for the first release: RADIUS accounting (1813), dynamic VLAN assignment, EAP-TLS client certificates, CoA/disconnect, RadSec, proxying to other RADIUS servers, and MAC authentication beyond a lab test.

## Identities

Network users are a separate table, not the `users` table. Reasons: Wi-Fi credentials are typed into many devices and leak more often than admin passwords; a Wi-Fi user should never be able to sign in to OpenManage; and household members need Wi-Fi accounts without being operators. Administrators manage network users from the UI, with the same audit and disable-not-delete rules as #56.

## EAP method

This is the main decision, because it fixes how passwords can be stored.

| Method | Client support | Password storage on the server | Protocol work |
| --- | --- | --- | --- |
| **EAP-TTLS with inner PAP** (recommended first) | Android, iOS/macOS, Windows 10+, Linux (wpa_supplicant); some older Android builds need the method picked by hand | bcrypt, like admin passwords, because the server receives the password inside the TLS tunnel | TLS over EAP fragments, then one Diameter-style AVP |
| PEAPv0 with EAP-MSCHAPv2 | Every common client, usually the default choice in the client UI | Needs the NT hash (unsalted MD4 of the password), which is password-equivalent if the database leaks | TLS over EAP fragments, inner EAP, MSCHAPv2 challenge/response and the MPPE key derivation |
| EAP-TLS | All clients, but each device needs a client certificate | No passwords | TLS only, plus certificate issuance and revocation |

Decision (Nishant, 2026-10-23): ship EAP-TTLS/PAP first, because it keeps passwords hashed with bcrypt and needs the least security-sensitive protocol code. Add PEAP-MSCHAPv2 only if a client that matters cannot do TTLS, and then store NT hashes encrypted with the existing AES-GCM key, never in plain form.

## Implementation outline

- RADIUS packet encoding (decided 2026-10-23): use `layeh.com/radius` (packet format, Message-Authenticator, attribute dictionaries) after checking its licence (MPL-2.0) and maintenance, or a small in-repo encoder if that dependency is not acceptable. The RADIUS layer is simple; EAP is the risk.
- EAP state machine in Go, keyed by RADIUS `State`, with a bounded number of concurrent conversations per AP and a short idle timeout.
- TLS: Go's `crypto/tls` running over an in-memory `net.Conn` that is fed by EAP-TTLS fragments (handling the length flag, more-fragments flag and ACKs). TLS 1.2 is required for broad client support; TLS 1.3 for EAP (RFC 9190/9427) can be enabled when clients support it.
- Key material: derive MS-MPPE-Send-Key and MS-MPPE-Recv-Key from the TLS exporter as RFC 5281 specifies, and send them encrypted with the AP's shared secret. This is the part most likely to be wrong in a way that only shows up on real clients, so it gets tests against `eapol_test` (from wpa_supplicant) in the lab before any phone test.
- Inner PAP: verify with bcrypt, rate-limited per username and per AP, with the same generic failure for unknown user, wrong password and disabled user.

## Server certificate

OpenManage generates a private CA and a server certificate (ECDSA P-256, 2-year lifetime) the first time RADIUS is enabled. Keys are stored encrypted like SSH keys. The UI shows the CA certificate's SHA-256 fingerprint and offers it for download, so clients can be told to trust that CA and check the server name. Without that step, clients that skip validation are open to an evil-twin AP collecting passwords; the UI says so plainly. An administrator can upload their own certificate and key instead.

## AP shared secrets

Each AP gets a random 32-byte secret, encoded as text, stored with AES-256-GCM bound to the device ID (as snapshots are). Requests are accepted only from the enrolled AP's address, with the right secret and a valid Message-Authenticator (required on every Access-Request, which also blocks the Blast-RADIUS attack). Rotating a secret uses the change workflow, so the AP and server switch together with rollback.

## Threat model (summary)

| Threat | Mitigation |
| --- | --- |
| Spoofed or replayed RADIUS packets on the LAN | Per-AP secrets, source address check, required Message-Authenticator, request authenticator checks, duplicate detection |
| Password guessing through an AP | Per-user and per-AP rate limits, audit of failures (username only), lockout notice in the UI |
| Evil-twin AP harvesting passwords | Server certificate with a downloadable CA and fingerprint; guidance to set CA and domain on clients |
| Database leak | bcrypt for TTLS passwords; AP secrets and certificate keys encrypted with the existing key |
| Bugs in EAP/TLS handling | Fuzz the EAP and TTLS parsers; bound fragment sizes and conversation counts; test with `eapol_test` and real clients before release |
| Listener exposed beyond the LAN | Off by default; binds to a configured LAN address; README warns against forwarding UDP 1812 |
